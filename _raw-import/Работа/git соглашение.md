## Памятка: Как писать информативные коммиты

**Цель:**  Писать понятные и лаконичные коммиты, которые помогут вам и вашей команде легко понимать историю изменений в проекте.

**Основные принципы:**

* **Повелительное наклонение:** Используйте глагол в повелительном наклонении (например, "Fix", "Add", "Update").
* **Краткость:**  Ограничьте сообщение коммита 50-70 символами.
* **Информативность:**  Кратко опишите суть изменений.
* **Подробное описание (опционально):**  Добавьте более детальное объяснение после краткого сообщения (через пустую строку).

**Примеры:**

**Хорошо:**

* `Fix: Исправлена ошибка валидации формы`
* `Feat: Добавлена поддержка загрузки файлов`
* `Docs: Обновлена документация API`
* `Refactor: Упрощена логика роутинга`
* `Chore: Удалены неиспользуемые компоненты`

**Плохо:**

*  `исправил баг` (неинформативно)
*  `Добавил кучу всего` (слишком общо)
*  `Изменения в файлах index.js, style.css, component.js` (не отражает суть изменений)

**Дополнительные советы:**

* **Ветки:** Используйте описательные названия веток (`feature/имя-функции`, `bugfix/описание-ошибки`).
* **Инструменты:** Используйте редакторы кода и Git-клиенты с поддержкой форматирования коммитов.
* **Согласованность:**  Придерживайтесь единого стиля написания коммитов в вашей команде.

**Помните:** Хорошие коммиты — это инвестиция в будущее вашего проекта.

Ошибка Unable to squash. Squashing replays all commits up to the last one required for the squash. A merge commit cannot exist among those commits. обычно возникает при использовании git rebase -i (интерактивное перебазирование)  с опцией squash  (объединить), когда в выбранном диапазоне коммитов есть один или несколько merge-коммитов. 

Почему это проблема:

- Merge-коммиты  создаются при объединении веток (например,  git merge) и имеют два родительских коммита. 
- `git rebase -i --squash`  пытается "проиграть" все коммиты линейно, чтобы объединить их в один. 
-  Присутствие merge-коммита нарушает линейность истории, и Git не может правильно выполнить squash.

Как это исправить:

1. Избегайте squash merge-коммитов:

   - В идеале, не включайте merge-коммиты в диапазон коммитов, которые вы хотите объединить с помощью squash.
   -  Выбирайте только те коммиты, которые идут последовательно друг за другом без разветвлений.

2. Используйте `rebase` без squash для merge-коммитов:

   - Если вам нужно изменить merge-коммит (например, исправить сообщение), используйте  git rebase -i без  --squash для этого коммита.
   - Вы сможете отредактировать сообщение, но сам merge-коммит останется в истории.

3. Альтернативные способы:

   - `git reset`: Если вы хотите полностью отменить мерж и вернуться к состоянию до него, используйте  git reset (с осторожностью!).
   - Ручное объединение изменений: В некоторых случаях, проще всего вручную перенести нужные изменения из коммитов, которые вы хотели объединить, а затем сделать новый коммит.

Рекомендации:

- Планируйте свои коммиты: Старайтесь делать  логические и атомарные  коммиты с самого начала, чтобы потом было проще управлять историей.
- Изучайте Git:  git rebase  — это мощный инструмент, но он может быть сложным. Уделите время изучению его возможностей и потенциальных проблем. 

Если у вас возникнут трудности с конкретным случаем, пожалуйста, опишите ситуацию подробнее (какие коммиты вы хотите объединить, какая ошибка возникает), и я постараюсь помочь.

## Branch

Название веток должно соответствовать шаблону:  
&lt;prefix&gt;/&lt;issue&gt;-&lt;name&gt;

**Типы веток:**
- feat — добавление нового функционала.
- fix — исправление существующего функционала.
- bug — исправление багов.
- enh — улучшение функционала (например, изменение бизнес-логики).
- refactor — рефакторинг (без изменения бизнес-логики или исправлений).
- docs — изменения в документации, README.
- test — изменения, связанные с тестированием (unit, E2E и т.д.).
- misc — изменения, связанные со сборкой и конфигурацией, такими как:
  - npm, 
  - Webpack, 
  - Vue CLI и т.д.

**Структура ветки:**
- &lt;issue&gt; — номер задачи (Redmine/Jira).
- &lt;name&gt; — краткое описание ветки.

**Пример названия ветки:**
feat/123-layers-panel

# Commit

Сообщения коммитов должны соответствовать [Соглашению о коммитах](https://www.conventionalcommits.org/ru/v1.0.0/).

&lt;type&gt;(&lt;scope&gt;): &lt;subject&gt;

&lt;description&gt;

<footer>

**Элементы сообщения коммита:**

- `<type>` — тип коммита. Возможные варианты:
  - enh — расширение/улучшение функционала.
  - feat — добавление нового функционала.
  - fix — исправление багов.
  - review — изменения, связанные с комментариями по ревью.
  - raise — изменения, не затрагивающие суть кода (например, форматирование, добавление точек с запятой, комментариев, JSDoc).
  - refactor — изменения в коде, не связанные с исправлением багов или добавлением новых функций.
  - perf — улучшения производительности.
  - build — изменения, затрагивающие сборку проекта (например, конфигурации Webpack, Vite, NPM).
  - ci — изменения, связанные с настройкой CI (например, скрипты для Node.js, конфигурации Webpack).
  - docs — изменения в документации.
  - test — добавление или изменение тестов.
  - chore — другие изменения, не затрагивающие код напрямую.

- `<issue>` — идентификатор задачи в трекере (Redmine/Jira).
- `<subject>` — краткое описание того, что было сделано.
- `<description>` — более детализированное описание изменений. Используется реже, например, при массовом рефакторинге или кодстайлинге.
- `<scope>` — область изменений, например:
  - core — базовая функциональность (Elem, Panel, render).
  - utils — утилиты.
  - ui — UI-компоненты.
  - api — типы, JSDoc.
  - common — общие части (менеджеры, хранилища, обработка ошибок).
  - infra — инфраструктура (CLI-утилиты, плагины, ESLint-правила, конфигурации).
  - types — типы и JSDoc.
  - style — стили CSS.

**Примеры сообщений коммитов:**

fix(#1234): исправлена ошибка в ElemImage

enh(#5678): улучшено поведение в ElemImage

- добавлена поддержка нового формата;
- оптимизирован рендеринг;
- улучшена логика обработки ошибок.
