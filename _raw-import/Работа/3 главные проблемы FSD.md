# ✅ 3 главные проблемы FSD после 3 лет реальной эксплуатации

|№|Проблема|Причина|Последствия|
|:-:|:--|:--|:--|
|1|**Слишком изменчивый `shared`**|`shared` находится внизу и на него ссылается всё приложение, хотя он содержит конкретные, часто меняющиеся вещи (UI Kit, API, config).|Любое изменение приводит к массовым поломкам в проекте. Ненадёжность кода.|
|2|**`Entities` не позволяют выразить бизнес-модель**|В `entities` запрещены кросс-импорты, а модель бизнеса — это связи между сущностями.|Невозможно полноценно описывать бизнес-логику, появляются лишние сложности с данными.|
|3|**Widgets + Features + Entities = High Coupling**|Стандартная декомпозиция по "фичам" и "сущностям" не учитывает реальное количество связей между модулями.|Высокая связность между частями кода. Сложная поддержка, разрастание зависимостей.|

---

# 🔥 Как исправить эти проблемы

|№|Решение|
|:-:|:--|
|1|Разделить `shared` на атомарные, независимые модули (`shared/ui`, `shared/lib`, `shared/api`, `shared/config`). Ограничить использование `shared` в слое моделей (`domain`, `model`). Избегать глобальных зависимостей.|
|2|Ввести дополнительный слой `models` (или `domain`), который описывает связи между сущностями. Связанные сущности объединять в агрегаты. Ограничить использование прямых кросс-импортов.|
|3|Изменить критерии декомпозиции: объединять плотно связанные сущности и действия в единые фичи. Учитывать связи при проектировании. Использовать инверсию зависимостей (`render props`, события, контекст) для взаимодействия.|

---

# 📋 Мини-памятка для улучшенного FSD

- `Entities` = агрегаты (плотные бизнес-группы).
    
- `Features` = слабосвязанные блоки функциональности.
    
- `Widgets` = только сборщики интерфейса, без бизнес-логики.
    
- Связи между фичами только через инверсию зависимостей (не прямые импорты).
    
- `Shared` используется только там, где это безопасно.
    
- Модель бизнеса (`domain/model`) изолирована от UI и инфраструктуры.

# 🧠 Вывод

Feature-Sliced Design — это **рабочая эвристика** для проектов со средним уровнем требований,  
но при росте сложности проекта его нужно адаптировать:

- усиливать защиту бизнес-модели,
    
- контролировать зависимости,
    
- учитывать реальное количество связей между модулями.
    

Если ничего не делать — проект на FSD через 1-2 года превратится в сложную для поддержки систему.
