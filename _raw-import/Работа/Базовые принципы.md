# 🎯 Базовые принципы

> [← к оглавлению серии](./📌 Введение в промпт-инжиниринг)

Семь правил, которые работают **всегда**, независимо от задачи. Их легко запомнить и легко применить.

## 1. Будь конкретным

Размытый промпт → размытый ответ. Это закон.

```plain
❌ Расскажи про производительность Vue
✅ Перечисли 5 главных причин медленных списков в Vue 3
   и покажи, как их фиксить (с кодом)
```

> [!tip]
> Если можешь подставить в промпт **число** (5 причин, 3 примера, 100 строк) — подставь. Это сразу убирает воду.


## 2. Дай контекст «зачем»

Один и тот же запрос с разной целью даёт разные правильные ответы.

```plain
❌ Напиши README
✅ Напиши README для open-source библиотеки.
   Аудитория — junior-разработчики, многие будут читать с телефона.
   Цель — чтобы человек за 30 секунд понял, нужна ли ему эта библиотека.
```

Контекст «зачем» помогает модели выбрать **правильный уровень детализации, тон и структуру**.

## 3. Укажи формат вывода

Без формата ты получишь то, что модель **угадает** на основе общих паттернов. Угадает часто плохо.

| Запрос | Без формата | С форматом |
|---|---|---|
| Сравни Pinia и Vuex | Длинный текст в духе блога | Таблица 2 колонки × 5 строк |
| Дай идеи pet-проектов | 10 идей абзацами | Нумерованный список с одной строкой описания |
| Объясни замыкания | 3 страницы теории | 1 пример + 1 абзац + 1 типичный баг |

> [!important]
> «Кратко» — недостаточно. Пиши **в каком виде**: таблица / список / артефакт / 3 предложения / JSON.


## 4. Раздели инструкции и данные

Когда в промпте есть и **что делать**, и **с чем делать** — отделяй явно. Иначе модель может перепутать данные с инструкциями.

Способ 1: XML-теги (Claude обучен на них — работает лучше всего)

```xml
<task>
Найди все computed, которые можно заменить на простые переменные.
</task>

<code>
... код компонента ...
</code>
```

Способ 2: разделители (если XML кажется громоздким)

```plain
ЗАДАЧА:
Найди логические ошибки в коде ниже.

**КОД:**
...
```

## 5. Итеративность — это норма

Первый промпт почти никогда не идеален. Это не провал, а часть процесса.

> [!info] Цикл доработки
> 1. Написал → отправил
> 2. Прочитал ответ → отметил, что НЕ так (формат? уровень? полнота?)
> 3. Допиши промпт уточнением: «короче / без воды / только код / больше деталей про X»
> 4. Повтори


В чате это особенно дешёво — не надо переписывать всё, можно просто сказать «то же самое, но в виде таблицы».

## 6. Тестируй на edge cases

Промпт, который хорошо работает на «нормальном» примере, **может развалиться** на:
- пустом вводе
- очень длинном вводе
- многоязычном тексте
- противоречивых условиях
- неоднозначных формулировках

Если промпт — для повторяющейся задачи (например, шаблон для написания коммитов или ревью кода), прогони его на 3–5 разных примерах **до** того, как сохранять как «свой workflow».

## 7. Длина ≠ качество

Длинный промпт ≠ хороший промпт. Иногда наоборот.

| Когда длинный — хорошо | Когда длинный — плохо |
|---|---|
| Много контекста, который нельзя сократить | Вежливые вступления и благодарности |
| Несколько примеров (few-shot) | Повторение одного и того же другими словами |
| Точные ограничения | Расплывчатые «постарайся сделать хорошо» |
| Структурированные данные | «Сделай это, а потом, если получится, ещё вот это, а также не забудь...» |

> [!warning]
> Если в промпте появляется слово «также» 5 раз — у тебя там **5 разных задач**. Разнеси их по разным сообщениям.


## Памятка из 5 пунктов

> [!info] Карманный чек
> 1. **Конкретно** (число, пример, предел)
> 2. **Контекст** (кто я, зачем мне это)
> 3. **Формат** (таблица / список / артефакт / N предложений)
> 4. **Раздели** инструкции и данные (XML или `###`)
> 5. **Итерируй** — не пытайся с первого раза


Этих 5 правил хватит, чтобы быть **выше 80% пользователей** Claude. Дальше — продвинутые штуки.
