# Организация работ

## Планирование спринта

### User Story

```
Формат:
Как [роль пользователя], я хочу [действие], чтобы [цель/ценность]

Примеры:
"Как покупатель, я хочу добавить товар в корзину, чтобы купить его позже"
"Как администратор, я хочу видеть отчёты продаж, чтобы принимать бизнес-решения"
```

### Story Points и оценка

```
Fibonacci: 1, 2, 3, 5, 8, 13, 21

1  — 1-2 часа (мелкое изменение)
2  — полдня
3  — 1 день
5  — 2-3 дня
8  — неделя (возможно, нужно разбить)
13 — слишком большое (нужна декомпозиция!)
```

### Velocity

```
Velocity = сумма Story Points за спринт
Среднее за 3 спринта = прогноз на следующий

Спринт 1: 34 SP
Спринт 2: 28 SP
Спринт 3: 31 SP
Средний velocity: ~31 SP/спринт
```

## Декомпозиция задач

### Принцип SMART

```
S — Specific    (конкретная)
M — Measurable  (измеримая)
A — Achievable  (достижимая)
R — Relevant    (актуальная)
T — Time-bound  (с дедлайном)
```

### Разбивка крупных задач

```
❌ "Разработать модуль авторизации" — слишком крупно

✅ Декомпозиция:
1. Создать форму логина (компонент + валидация) — 3SP
2. Интеграция с API авторизации — 2SP
3. Хранение JWT токена (store) — 2SP
4. Route guards (защита роутов) — 2SP
5. Страница "Сброс пароля" — 3SP
6. Тесты авторизации — 3SP
```

### Definition of Done (DoD)

```markdown
Задача считается выполненной если:
- [ ] Код написан согласно стилю проекта
- [ ] Покрытие тестами > 80%
- [ ] Code review пройден
- [ ] CI/CD пройден без ошибок
- [ ] Задача задеплоена на staging
- [ ] Принята заказчиком/product owner
```

## Git-стратегия в команде

### GitFlow

```
main     ─────────────────────────────── (продакшн)
              ↑ merge             ↑ hotfix
develop  ─────────────────────── (интеграция)
              ↑              ↑
feature/  auth-login    cart-module
```

### Trunk-Based Development

```
main  ────────────────────────── (основная ветка)
        ↑ short-lived ↑
      feature  feature
      (< 1 день жизни)
```

**Когда что:**
- GitFlow — строгие релизы, несколько окружений
- Trunk-Based — CI/CD, частые деплои, feature flags

## Code Review практики

### Что проверять в ревью

```markdown
Функциональность:
□ Код делает то, что описано в задаче
□ Граничные случаи обработаны
□ Нет регрессий

Качество кода:
□ Читаемость (понятны имена переменных)
□ Нет дублирования (DRY)
□ Компоненты не перегружены ответственностью (SRP)

Безопасность:
□ Нет SQL инъекций, XSS
□ Данные пользователя не логируются
□ Авторизация проверяется корректно

Производительность:
□ Нет ненужных ре-рендеров
□ Тяжёлые операции закэшированы
□ Нет N+1 запросов
```

### Культура ревью

```
❌ "Этот код — мусор"
✅ "Можно рассмотреть другой подход: [пример]. Это улучшит производительность при..."

❌ "Почему ты так сделал?"
✅ "Я вижу, что здесь используется X. Рассматривал ли Y? Он даёт..."

Нитпик (nit): незначительное замечание — не блокирует мерж
```

## Технический долг

### Категории техдолга

```
Намеренный:
"Мы знаем что это некачественно, но нам нужно выпустить в срок"
→ Фиксируется в backlog с ticket

Случайный:
"Мы не знали лучшего способа в тот момент"
→ Обнаруживается при ревью или рефакторинге
```

### Управление техдолгом

```
Стратегия Boy Scout: "Оставь код немного чище, чем нашёл"
- При работе с модулем — улучши 1 вещь рядом

Выделение времени:
- 20% спринта на рефакторинг
- Отдельные "tech debt спринты" раз в квартал

Приоритизация:
Critical: блокирует работу (фиксируется немедленно)
High:     влияет на производительность команды
Medium:   неудобно, но терпимо
Low:      улучшение стиля, именования
```

## Инструменты организации работы

```
Трекинг задач:
- Jira     — сложные проекты, enterprise
- Linear   — быстрые startup-команды
- GitLab Issues — интеграция с кодом
- GitHub Projects — для open-source

Коммуникация:
- Slack / Teams — ежедневное общение
- Confluence / Notion — документация

CI/CD:
- GitLab CI — интегрировано с репозиторием
- GitHub Actions — гибкие воркфлоу
- Jenkins — enterprise
```

## Встречи команды

```
Daily Standup (15 мин):
- Что сделал вчера?
- Что планирую сегодня?
- Есть ли блокеры?

Sprint Planning (2-4 часа):
- Выбрать задачи из backlog
- Оценить SP
- Определить цель спринта

Sprint Review (1 час):
- Демонстрация готового функционала
- Получение обратной связи

Retrospective (1 час):
- Что прошло хорошо?
- Что улучшить?
- Action items с ответственными
```
